# SOCITAS Ruleset v2

Ankündigung für alle AL-Entwickler. Kurzfassung: v2 ist ein neuer, optionaler Analyzer-Stack mit strengerem Ruleset.
Kein Repository wird automatisch migriert; ein Repo wechselt, wenn **ihr** es im ersten PR eures nächsten Tickets dort umstellt.

## Was ist v2

**Stack.** v2 prüft mit:

- den Microsoft-Cops (`${CodeCop}`, `${UICop}`, `${PerTenantExtensionCop}`, `${AppSourceCop}`, wie bisher im Repo gewählt),
- **ALCops** (ersetzt LinterCop, der upstream in ALCops aufgegangen ist),
- **SocitasCopV2** (ersetzt SocitasCop v1),
- für **Test-Apps** zusätzlich **TestCop**.

Nicht Teil von v2: `BusinessCentral.LinterCop.dll` und `BusinessCentral.SocitasCop.dll`.

**Gepinnte Versionen** (`SOCITAS.analyzers.v2.json`, aktuell `revision` 1):

| Komponente | Version |
|---|---|
| ALCops | 1.3.1 |
| SocitasCopV2 | 1.0.0 |
| TestCop | 0.1.0 |
| AL-Compiler (Referenz für das Regelinventar) | 18.0.43.1464 |

Neue Upstream-Releases ändern nie ein Build-Ergebnis. Eine neue Version wird nur durch einen bewussten PR auf BCRuleset
angehoben; derselbe PR gibt allen neuen Regeln eine explizite Aktion im v2-Ruleset.

**Rulesets.**

- `SOCITAS.ruleset.v2.json`: App-Ruleset, für jede Regel des v2-Stacks eine explizite Aktion (CI prüft die Vollständigkeit gegen die gepinnten Versionen).
- `SOCITAS.test.ruleset.v2.json`: Test-Ruleset, **generiert** (nie von Hand ändern) aus dem App-Ruleset, den weiterhin nötigen Test-Lockerungen und den TestCop-Regeln (`ST0001` = Error).
  Jede Lockerung des v1-Test-Rulesets ist in `v2/test-relaxations.json` festgehalten: behalten (5), umgeschrieben auf neue Ids (2) oder verworfen (2), jeweils mit Begründung.
- Basis-URL: `https://socitas-gmbh.github.io/BCRuleset/<Datei>`.

**v1 bleibt.** v1 ist eingefroren (`SOCITAS.ruleset.json`, `SOCITAS.test.ruleset.json` ändern sich nicht), wird ohne Frist weiter unterstützt, und LinterCop ist auf seine letzte Version gepinnt
(RapidCompile: NuGet 0.41.2, Container-Pfad: Release v0.40.1). Ein Repo auf v1 baut wie bisher.

**v2 wird zentral gesteuert** und darf in place verschärft werden. Vorher ist sichtbar, welche v2-Repos die Verschärfung rot machen würde
(Vorschau-Report, siehe „Schweregrad-Änderung vorschlagen“).

## Migration

**Wann:** als erster PR eures nächsten Tickets in dem Repo. Es gibt keine Sammelaktion und keinen Pipeline-Parameter.

```powershell
# 1. Trockenlauf: zeigt, was sich ändern würde
tools/Convert-RepoToV2.ps1 -RepoRoot <pfad-zum-repo> -WhatIf
# 2. Anwenden
tools/Convert-RepoToV2.ps1 -RepoRoot <pfad-zum-repo>
```

Das Skript (`tools/Convert-RepoToV2.ps1` im BCRuleset-Repo, Windows PowerShell 5.1 oder 7) erledigt pro Projekt mit `.vscode/settings.json`, das noch v1-Merkmale trägt:

- **Analyzer-Liste** (`al.codeAnalyzers`): entfernt LinterCop und SocitasCop v1, ergänzt die kanonische v2-Liste (Test-Projekte: inkl. TestCop); `${…Cop}`-Einträge und unbekannte Einträge bleiben.
- **Ruleset-Include**: `SOCITAS.ruleset.json` wird `SOCITAS.ruleset.v2.json`, `SOCITAS.test.ruleset.json` wird `SOCITAS.test.ruleset.v2.json`.
- **Lokale Regel-Ids** im Repo-Ruleset: LinterCop-Ids werden über `LinterCop-to-ALCops.json` auf ALCops-Ids abgebildet (eine Id kann mehrere Ziele haben).
- **Pragma-Ids**: in `#pragma warning disable|restore <ids>` werden die Ids ebenso abgebildet; sonst bleibt jede Datei byte-identisch.

Das Skript ist idempotent (zweiter Lauf ändert nichts) und fasst nichts außerhalb von `-RepoRoot` an.

**Bleibt bei euch:**

- die gemeldeten **Diagnosen beheben** (v2 ist strenger; das Skript behebt nichts),
- **Ids ohne ALCops-Entsprechung**: das Skript meldet sie als `unmapped: …` und lässt sie stehen; ihr entscheidet, ob die Regel entfällt oder ersetzt wird,
- Rulesets außerhalb des Repos oder nicht gefundene Rulesets: nur als `note:` gemeldet, nicht geändert.

**Pipeline-YAML:** keine Änderung. CI erkennt v2 allein daran, dass das Ruleset, mit dem das Projekt baut (`al.ruleSetPath`), ein v2-Ruleset einbindet.
Auf v2 muss die Analyzer-Liste der kanonischen Liste entsprechen; fehlt ein Eintrag oder steht LinterCop/SocitasCop v1 drin, bricht der Build mit Namen des Eintrags ab.
Lässt sich ein v2-Analyzer nicht laden oder stürzt er ab, bricht der Build ebenfalls ab und nennt ihn.

**Größe des Jobs vorher abschätzen:** für Repos auf v1 sendet CI auf main, stage und dev bereits Telemetrie (`CI Preview Compile`, Modus `v2`) mit den Diagnosen, die v2 melden würde
(App und, sofern vorhanden, Test-App; inkl. SocitasCopV2 und TestCop), und mit `wouldFailBuild`. Das ändert das Build-Ergebnis des Repos nie.

## Lokales Setup

In VS Code den Befehl **„SOCITAS AL: Download v2 Analyzers“** (SocitasAL-Extension) ausführen. Er liest `SOCITAS.analyzers.v2.json` und installiert **genau die in CI gepinnten Versionen**
(ALCops von nuget.org, SocitasCopV2 und TestCop aus den GitHub-Releases der `socitas-gmbh`-Repos) in den Analyzer-Ordner der AL-Extension.
Ist die Pins-Datei nicht erreichbar, nutzt er eingebaute Pins (Revision 1). TestCop liegt in einem privaten Repo: VS Code fragt nach einem GitHub-Login.
Danach **das Fenster neu laden**.

Mit denselben Versionen und demselben Ruleset sind Regel-Ids und Schweregrade gleich wie in CI.

**Nach einer Pin-Erhöhung:** den Befehl erneut ausführen und das Fenster neu laden. Der Befehl läuft nicht automatisch (anders als „Download LinterCop“ für v1, das unverändert bleibt).
Neue Repos, die mit der SocitasAL-Extension angelegt werden, starten bereits mit der v2-Analyzer-Liste und dem v2-Ruleset-Include.

## Schweregrad-Änderung vorschlagen

1. PR auf das BCRuleset-Repo, der **`SOCITAS.ruleset.v2.next.json`** ändert (Kandidat; analog `SOCITAS.test.ruleset.v2.next.json` bzw. `SOCITAS.analyzers.v2.next.json`). Die produktiven v2-Dateien bleiben unberührt.
2. Die Pipelines von Repos auf v2 kompilieren auf main/stage/dev den Kandidaten als Vorschau (Modus `v2.next`) und melden `wouldFailBuild`; der Report `tools/Get-V2ImpactReport.ps1` listet je v2-Repo, ob der letzte Build rot würde (`fail`/`pass`/`not evaluated`).
3. Erst nach Prüfung des Reports wird der Kandidat in die produktive Datei übernommen (`tools/Test-V2Promotion.ps1`: eine geänderte v2-Datei muss ihrer `next`-Datei auf dem Basis-Branch entsprechen).

Ablauf im Detail (Vorschlag, Vorschau, Übernahme, Pin-Bump): [v2-aenderungen.md](v2-aenderungen.md).

## Noch nicht verfügbar / Einschränkungen

- **SC0046–SC0052**: stehen im Quellcode von SocitasCopV2, aber nicht im gepinnten Release 1.0.0 (das v2-Ruleset deckt SC0001–SC0045 ab). Sie brauchen ein neues SocitasCopV2-Release und eine Pin-Erhöhung.
- **TestCop-Befunde in RapidCompile-CI**: RapidCompile kompiliert keine Test-Apps. TestCop-Befunde kommen aus dem Container-Pfad, lokal in VS Code oder aus der Preview-Telemetrie.
- **Impact-Report von Hand**: `Test-V2Promotion.ps1` läuft in `validate.yml` bei jedem Pull Request; der Impact-Report (`tools/Get-V2ImpactReport.ps1`) läuft dagegen von Hand und braucht Lesezugriff auf den Log-Analytics-Workspace.
- **Nicht belegt**: dass lokal und CI auf einem Commit identische Ids/Schweregrade melden, ist durch ein Canary-Repo noch nicht nachgewiesen.
- Technische Details für CI: `docs/RapidCompile-Technische-Referenz.md` im Repo BuildTemplates.
